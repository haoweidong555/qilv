# 栖旅 · 城市数据字典（v0.2 · 已确认关键决策）

这份文档定义"一座城市到底由哪些数据构成"。它是数据采集、界面设计、后台结构、
以及将来对外解释"你们的指数怎么来的"的唯一依据。

**先立三条铁律**，后面所有字段都服从它：

1. **没有数据就不显示。** 缺失一律显示"暂无数据"，严禁用 0 或默认值填充
   —— 用户看到的每个 0 都会被当成真实结论。
2. **众包数据必须带样本量和时间。** 少于 30 个样本的评分不显示分数，只显示"样本不足"。
3. **每个字段都要能回答三个问题**：哪来的、什么时候更新的、谁校核的。
   页面上的每个数字都应该能点开看到来源。

---

## 0. 每个字段的四个元信息

任何字段落到数据库里，都必须同时带上这四项（缺一不可）：

| 元字段 | 含义 | 示例 |
| --- | --- | --- |
| `source` | 来源 | `统计年鉴2025` / `高德POI` / `用户投稿` / `平台实测` |
| `updatedAt` | 采集或校核时间 | `2026-09-20` |
| `confidence` | 可信度等级（见下） | `B` |
| `sampleSize` | 样本量（众包/实测类必填） | `42` |

**可信度等级**（决定页面上怎么标注）：

| 等级 | 定义 | 展示方式 |
| --- | --- | --- |
| **A** | 官方统计或权威公开数据 | 直接显示，标注来源与年份 |
| **B** | 平台实测／多源交叉验证 | 显示，标注"平台实测 + 日期" |
| **C** | 用户众包（需样本量） | 显示中位数 + 样本量，样本 <30 只显示"样本不足" |
| **D** | 估算／推算（含 AI 生成的初稿） | **必须标"估算"**，不可作为筛选默认值 |

> 现在原型里 69 座城市的成本、网速、指数全部是 **D 级**（示例口径）。
> 也就是说：**目前没有一个数字可以直接上线**，这份字典就是要把它们升到 A/B/C。

## 已确认决策（2026-09-27）

| # | 议题 | 决策 | 落地要求 |
| --- | --- | --- | --- |
| 1 | 成本的构成 | **由产品侧定义**，口径见 §2-B（含房租、含三餐、不含大交通与旅游） | 口径带版本号 `costMethod: v1`，每次调整升版本，历史数据不混用 |
| 2 | 房租取价 | **挂牌价与成交价并列**，两者都展示，并额外算出"议价空间" | 成交价样本不足时**留空**，不用挂牌价推算填充 |
| 3 | 旅居指数 | **算法与权重公开**，页面上可展开查看 | 权重改版要在页面上留版本与生效日期 |
| 4 | 众包评分门槛 | **样本 ≥30 才显示分数** | 30–99 显示分数＋样本量；<30 显示"样本不足" |
| 5 | 城市粒度 | **收录县级市、自治州、地区**（阳朔、婺源、稻城、甘孜、海西、神农架等） | 展示仍用"省 · 市/县"两级，不细分景区与街道 |

> 这 6 条一旦执行，会反过来约束界面：**"议价空间"和"算法公开"都必须在页面上有位置**，
> 否则等于没做。

## 1. 数据分层与命名

**空间粒度**：只到"市级/县级市/自治州"。直辖市、特别行政区按一条计；自治州、地区按一条计；
**县级市与县也收录**（阳朔县、婺源县、平遥县、黟县、巴马县、凤凰县、漠河市…），
因为国内真正有旅居价值的地方，很多并不在地级市名单里。
但仍**不做景区级与街道级数据**（不做"洱海西岸""日月湾"），
—— 那一层的维护成本是市级的 5–10 倍，而用户决策主要发生在城市层面。

**命名**：字段名用 camelCase，直接对应 `assets/js/data.js` 里的键，
避免文档与代码两套叫法。分组前缀：`base*` `cost*` `net*` `cli*` `tra*` `med*`
`safe*` `life*` `sys*` `nomad*`。

### B. 成本（15）

成本是最容易引起争议的一组。因为"一个月要花多少"人人答案不同，
所以口径必须写成**像合同一样清楚**，并且带版本号。

#### B1. 月均总成本 `costMonthly` —— 口径 v1（2026-09-27 定）

**一句话定义**：一个**单身远程工作者**在**该城市市区**，
按**普通本地生活方式**住满一个月的现金支出。

**包含**（六项）：

| 项 | 默认假设 | 说明 |
| --- | --- | --- |
| 房租 | 一居室整租，取**成交价中位**；成交样本不足时用"挂牌中位 × 议价系数"并在页面标注为估算 | 口径见 B2 |
| 水电燃气网络 | 按年均月摊（夏冬取平均） | 北方含取暖费、南方不含（因取暖差异大，单列） |
| 餐饮 | **60% 自炊 + 40% 外食** | 页面上允许用户改比例（见下） |
| 市内交通 | 公交/地铁月票 + 每周 3 次打车（3km 内） | 不含跨城 |
| 日用品与通讯 | 手机费、洗护、洗衣等 | 固定小项 |
| 娱乐杂项 | 每月 2 次咖啡馆 + 2 次电影/展览 | 不含酒局与旅游 |

**不包含**（必须在页面注明）：
往返大交通（机票/高铁）、大额医疗与保险、数码设备购置、旅游与社交酒局、宠物开销。

**宠物的处理**：单列 `costPet`（元/月），因为带宠与不带宠差异极大，混在一起会让两边都不满意。

**允许用户改假设**：页面上给一个"按我的习惯算"的滑杆/开关
（自炊比例、是否打车、是否要共享办公），实时重算 `costMonthly`。
这是把"口径争议"转成"用户参与"的最省事办法 —— 也是 Nomad List 的做法。

#### B2. 租金：挂牌与成交并列

**为什么两个都要**：挂牌价反映房东预期，成交价反映真实行情，
两者的差额本身就是最有价值的信息 —— "这个城市的房租能砍下多少"。

| 字段 | 单位 | 口径 | 来源 | 更新 | 等级 | 筛 |
| --- | --- | --- | --- | --- | --- | --- |
| `rentRoomDeal` | 元/月 | 合租单间**成交**中位 | 用户实测 + 中介核价 | 每季度 | C | 是 |
| `rent1brCenterList` | 元/月 | 市区（距市中心 5km 内）一居室**挂牌**中位，排除服务式公寓与短租 | 贝壳/链家/58 公开挂牌 | 每季度 | B | 是 |
| `rent1brCenterDeal` | 元/月 | 同上，**成交**中位（样本 ≥20 才展示） | 用户实测 + 中介核价 | 每季度 | C | 是 |
| `rent1brSuburbList` | 元/月 | 近郊/新区一居室挂牌中位 | 同上 | 每季度 | B | 是 |
| `rent1brSuburbDeal` | 元/月 | 同上成交中位 | 同上 | 每季度 | C | 是 |
| `rentWholeList` | 元/月 | 两居或整院**挂牌**中位（旅居常见的"整院"归这里） | 同上 | 每季度 | B | 是 |
| `rentWholeDeal` | 元/月 | 同上成交中位 | 同上 | 每季度 | C | 是 |
| `bargainGap` | % | **议价空间** = (挂牌 − 成交) / 挂牌，自动计算 | 由上面两项推导 | 每季度 | B | 是 |
| `rentTerms` | 文本 | 常见付款方式：押一付一／押一付三／押二付一 | 用户投稿 | 每半年 | C | 否 |
| `rentSeasonUplift` | % | 旺季相对淡季的**租金**涨幅（不是酒店价） | 挂牌价对比 | 每半年 | B | 是 |

> 成交价样本不足时**留空**，不用挂牌价折算填充 —— 一旦用户发现我们"编"了成交价，
> 整组数据的信任就没了。

**舒适度算法必须公开**（页面可展开查看），建议口径：

```
comfort = 100 - |月均气温 - 21| × 2.4
        - 极端高温扣分（>32℃ 扣 10，>36℃ 再扣 8）
        - 极端低温扣分（<-5℃ 扣 6）
        - 湿度修正（回南天/梅雨月 -6；干燥月 -3）
        - 雨季修正（月降水极值 -5）
        下限 32，上限 94
```

### I. 旅居适配与社区（8）

| 字段 | 单位 | 口径 | 来源 | 更新 | 等级 | 筛 |
| --- | --- | --- | --- | --- | --- | --- |
| `nomadIndex` | 0–100 | 旅居指数（权重见下，**已确认在页面公开**，带版本与生效日期） | 平台自研 | 每季度 | B | 是 |

**旅居指数权重（建议 v1，公开在页面上）**：

```
nomadIndex = 成本 25% + 气候 20% + 网络 15% + 生活配套 15%
           + 安全 15% + 社区活跃 10%
```

> 这个权重意味着：**贵的城市天然排名靠后**（北京 73、上海 79 vs 大理 92）。
> 这是"旅居指数"应有的定义（衡量长住性价比），但一定要在页面写清楚，
> 否则会被理解成"城市排名"而引发争议。

### K. 景点与玩乐（3，首屏筛选项新增）

你要求首屏能按"旅游景点"和"特色奶茶店"筛，这两个都必须落到字段上，才不会变成运营口头描述。

| 字段 | 单位 | 口径 | 来源 | 更新 | 等级 | 筛 |
| --- | --- | --- | --- | --- | --- | --- |
| `attractionsTop` | 文本数组 | 3–5 个**代表景点**（编辑归纳，按旅居视角选：可反复去、非一次性打卡） | 文旅部名单 + 公开资料 + 编辑 | 每年 | B | 是 |
| `attractionsA45` | 家 | 该市 4A/5A 级景区数量 | 文旅部 A 级景区名录 | 每年 | A | 是 |
| `attractionSeason` | 月数组 | 该市最佳游玩季节（可与 `bestMonths` 不同：前者是旅居适宜期，后者是观光最佳期） | 编辑 + 公开资料 | 每年 | B | 是 |

**说明**：`bestMonths`（适合长住）和 `attractionSeason`（适合观光）**必须分开**——
很多地方的观光旺季恰恰是旅居最不舒服的时候（人挤、涨价、太热）。混在一起会让两边都失真。

### L. 特色奶茶店（3，首屏筛选项新增）

你要求首屏能按"特色奶茶店"筛。这里要诚实分层：**门店数量与代表品牌可以从公开地图数据拿到，
但"哪家好喝"的评分目前没有公开数据源**，只能等阶段二用户补充。

| 字段 | 单位 | 口径 | 来源 | 更新 | 等级 | 筛 |
| --- | --- | --- | --- | --- | --- | --- |
| `milkTeaCount` | 家/km² | 奶茶饮品门店密度（地图 POI 分类检索） | 高德开放平台 POI | 每半年 | B | 是 |
| `milkTeaBrands` | 文本数组 | 代表品牌 + 本地特色店（3–5 个，编辑归纳，注明是"当地有、别处没有"的店） | 公开资料 + 编辑 | 每半年 | C | 是 |
| `milkTeaScore` | 0–5 | 奶茶综合评分（**阶段二众包**，样本 ≥30 才显示） | 用户投稿 | 实时累计 | C | 是 |

**阶段一先上什么**：`milkTeaCount` + `milkTeaBrands` 都能立刻采到；
`milkTeaScore` 留空并显示"等你来评"——这正好也是把用户引进阶段二的钩子。

> **原型里的临时口径（2026-09-27）**：原型已经能按"特色奶茶店"筛，但门店密度还没跑
> POI，用的是**按城市类型分的三档粗估**（城市型=多 / 湖畔海岸=一般 / 草原雪山=少见），
> 代表品牌只填了少数确定能确认的本地品牌（长沙茶颜悦色、郑州蜜雪冰城、成都茶百道、
> 昆明霸王茶姬等）。**上线前必须用 `milkTeaCount` 实测值替换这三档**，
> 否则用户会当成真实密度看。

## 3. 展示与缺失规则

1. 缺失显示"暂无数据"，**不显示 0**；数字类字段缺失时，该城市不参与以该字段排序。
2. 众包评分：样本 <30 → 显示"样本不足"；30–99 → 显示分数 + "样本 N"；≥100 → 显示分数 + "样本 N（近 90 天）"。
3. 所有 A/B 级数据在详情页可点击查看来源与更新时间；C 级显示样本量与采集区间；D 级必须带"估算"角标。
4. 筛选器里出现的字段，默认只用 A/B/C 级数据；D 级数据不参与默认排序。
5. 单价类字段统一显示中位数，并在 tooltip 说明"中位数，非平均"。

## 5. 数据来源与获取方式（两阶段策略）

**已确认的路线**：**前期全部依赖网上公开信息**（不做出差实采、不买数据），
**后期由用户自主补充**（众包评分、实测数据、素材上传）。这条路线决定了哪些字段能先上、哪些必须等。

### 阶段一：公开信息（上线前 → 上线初）

只用公开可查的数据，每个数字都要能贴出链接。

| 类型 | 具体来源 | 获取方式 | 自动化 | 坑 |
| --- | --- | --- | --- | --- |
| 行政区划 | 民政部行政区划信息查询平台、国家统计局统计用区划代码 | 网页摘录 | 可 | 每年有调整，要记版本 |
| 人口 / GDP | 国家统计局年鉴、各省统计年鉴 | 网页摘录 | 半自动 | 年鉴口径与年份要标清 |
| 气温 / 湿度 / 日照 / 降水 | 中国气象数据网、和风天气 API、OpenWeather | API + 历史数据 | 可 | 分清"月均/年均/实时" |
| 空气质量 | 全国城市空气质量实时发布平台、OpenAQ | API | 可 | AQI 有国标/美标两套，必须注明 |
| 三甲医院 | 国家卫健委及各省卫健委三级医院名单公示 | 名单摘录 | 半自动 | 名单按批次公布，注意有效期 |
| 异地医保结算 | 国家医保服务平台公开查询、各地医保局公示 | 人工核对 | 否 | 政策变动频繁，半年复检 |
| 集中供暖 | 各市供暖条例、政府公开文件 | 人工整理 | 否 | 要写清供暖期起止，不只是一个"有/无" |
| 高铁 / 机场 | 12306 时刻表、民航局机场名单 | 人工抽样 | 否 | 12306 有反爬，建议人工查 5 个枢纽线路 |
| 地铁线路 | 各市地铁集团官网与年报 | 网页摘录 | 半自动 | 年度更新 |
| 房租挂牌价 | 中国房价行情网、贝壳/链家公开页面 | 人工抽样 20 条取中位 | 否 | **不要大规模爬取**；抽样要记录日期与样本 |
| 网速 | 宽带发展联盟季度报告、Speedtest Global Index | 公开报告摘录 | 半自动 | 是城市均值，不是你家实测；需注明 |
| 可办公咖啡馆 / 共享办公 / 菜市场 / 驿站 | 高德开放平台 POI 检索 API、腾讯位置服务 | API（免费配额） | 可 | **必须用有资质服务商**；"可办公"要人工抽查 |
| 步行友好度 | 高德步行路网 + POI 密度自算 | API + 算法 | 可 | 算法要写清 |
| 方言难度 / 城市气质标签 | 公开资料 + 媒体描述 | 人工归纳 | 否 | 标注为"编辑判断" |

**阶段一明确不做**（没有公开来源，硬做就是编）：
外卖平均配送时长、奶茶门店评分、菜市场满意度、宠物友好度——
这些**等阶段二靠用户补充**，现在留空显示"暂无数据"。

### 阶段二：用户自主补充（上线后持续）

| 类型 | 能补什么 | 门槛与规则 |
| --- | --- | --- |
| 实测网速 | `netDown` / `netUp` 的真实样本 | 需上传测速截图或链接 + 记录城市与月份 |
| 实付租金 | `rent*Deal` 成交价、议价空间 | 需手机号实名 + 单账号单城市一次，防刷 |
| 生活评分 | 奶茶、餐饮、夜生活、菜市场、方言难度 | 样本 ≥30 才显示；评分记录账号与时间，可审计 |
| 安全评分 | 治安、女性夜间安全（分人群） | 女性样本单独统计；样本 ≥30 |
| 避坑内容 | `scamRisk`、`watchouts` | 需提供具体地点与时间；编辑复核 |
| 实拍素材 | `mediaSource` / `mediaCredit` / `mediaLicense` | 必须勾选授权条款，否则不入库 |
| 成本核对 | `costMonthly` 的本地实付校准 | 与阶段一的公开推算交叉验证，偏差 >20% 要人工复核 |

> **两阶段的关系**：阶段一的公开数据负责"让页面有内容、能上线"，
> 阶段二的用户数据负责"让数据可信、有独家性"。
> 用户补充的数据优先级永远高于公开推算 —— 一旦某城有 30 条真实实付租金，
> 就把公开推算降级为参考值，并在页面上显示"数据来自 N 位旅居者"。

## 8. 采集与合规注意事项（不是法务意见，但必须提前问）

1. **地图**：底图必须用有测绘资质的服务商 SDK；不得自行绘制或发布中国地图（含国界线）。
2. **位置信息**：属于敏感个人信息，需单独同意；建议默认只到"城市级"，不采集精确坐标。
3. **用户投稿**：用户协议里必须写明"平台可在站内及关联渠道使用用户上传的内容"，
   否则将来做宣传素材时会侵权。
4. **爬虫**：房产与 POI 数据抓取前先看对方条款与 robots；优先走官方 API。
5. **评分公正性**：一旦出现商家刷分，"数据可信"这个核心资产就没了；
   建议从第一天就记录评分来源账号与时间，保留审计能力。
